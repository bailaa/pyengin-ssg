(длительность job и шагов из API GitHub), раннер `ubuntu-24.04`.

### Время доставки

| Метрика | GitHub Pages (`pages.yml`) | Helios (`helios.yml`) |
|---|---|---|
| Запусков в выборке | 4 успешных на `main` | 3 успешных (2 на `main`, 1 preview) |
| plan (вычисление слота, URL) | — | 3 с |
| build: установка + `mkdocs build --strict` | 14–19 с (lint 4–7 с) | 19–21 с (lint 4–6 с) |
| Загрузка | артефакт в Pages | rsync в `releases/` — 6–7 с |
| Публикация | `deploy-pages` 5–7 с | `ssg activate` — 2–3 с |
| Healthcheck | 0–1 с | 1–2 с |
| deploy, всего | 10–11 с | 17–20 с |
| **push → сайт обновлён** | ≈ 26–30 с | ≈ 40–44 с |
| Откат на предыдущий релиз | повторный запуск старого workflow (≈ 30 с) | `workflow_dispatch: rollback` — job целиком 17 с, сама операция 2–3 с, **без пересборки** |

Выборки маленькие (3–4 запуска), поэтому это порядок величин, а не статистика. Один из запусков Pages дал выброс:
шаг `deploy-pages` занял 73 с вместо 5–7 (job deploy — 78 с). У Helios такого разброса в выборке не было,
но у него и меньше звеньев вне нашего контроля.

### Сравнение площадок

| Критерий | GitHub Pages | Helios |
|---|---|---|
| Время доставки | быстрее (≈ 28 с против ≈ 42 с), но с редкими выбросами | ≈ 42 с, 6–7 с из них — rsync |
| Надёжность | управляемая платформа, CDN, атомарная публикация артефакта | один сервер университета; публикация копированием, не атомарна (см. ниже) |
| Доступность | с раннеров и с Mac отвечает (200) | **с Mac через VPN в Нидерландах не отвечал**, с раннеров GitHub отвечает — доступность зависит от сети клиента |
| Удобство отладки | весь процесс выкладки скрыт внутри `deploy-pages`; на выброс 73 с повлиять нельзя | свой bash: видно каждую команду rsync/ssh и отказы шлюза (`ssg-gate: запрещено: опция --stats`) |
| Preview веток | нужен отдельный механизм | из коробки: `preview/<ветка>/` |
| Откат | перезапуск старого деплоя | один шаг, 2–3 с, предыдущие 5 релизов на диске |
| Права при компрометации | токен только на Pages | ключ ограничен шлюзом, но это полный контроль над содержимым `~/public_html` |

| Автооткат при провале проверки | **не воспроизведён на реальном сервере**: провалить healthcheck после активации, не ломая `main`, нельзя | логика проверена чтением; ручной откат проверен отдельно |

!!! note "Побочное наблюдение"
    Любой push в `main`, включая правку workflow-файла диагностики, запускает деплой и создаёт новый релиз.
    Поэтому «предыдущий» релиз для отката — это предыдущий по **времени активации**, а не по смыслу.
    Для точного возврата на нужную версию используется `rollback` с параметром `release`.
